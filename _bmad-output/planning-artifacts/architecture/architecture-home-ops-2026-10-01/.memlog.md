- (decision) The architecture paradigm is declarative GitOps reconciliation with layered Kubernetes composition: Git is the desired-state source, Flux reconciles it, Kustomize composes resources, and HelmRelease/OCI artifacts install packaged controllers and workloads. This prevents independently authored units from choosing imperative deployment as a second source of truth. Evidence: README.md; kubernetes/apps/flux-system; Flux official documentation.
- (decision) Kubernetes ownership is split into platform namespaces (flux-system, network, vault, cert-manager, longhorn-system, kube-system, observability, database) and workload namespaces such as default and gpu. Platform services establish the contracts consumed by workloads; workload manifests must remain under kubernetes/apps and be composed through their namespace/application Kustomization boundary. Evidence: kubernetes/apps directory structure and Flux Kustomization paths.
- (decision) Flux Kustomization dependencies are the ordering contract. A unit that consumes another platform capability must declare dependsOn and, where readiness matters, wait and healthCheckExprs. This prevents race-dependent installations and hidden ordering encoded only in filenames. Evidence: kubernetes/apps/longhorn-system/longhorn/ks.yaml, kubernetes/apps/cert-manager/cert-manager/ks.yaml, kubernetes/apps/database/cnpg/ks.yaml, kubernetes/apps/vault/vault-secrets-operator/ks.yaml.
- (decision) Secrets have two ownership paths: repository/bootstrap secrets are encrypted with SOPS and decrypted by Flux through the sops-age secret; runtime application secrets are materialized from Vault using VaultAuth and VaultStaticSecret resources, with SecretStore used where an external provider integration requires it. Plaintext secret material must not become a repository source. Evidence: .sops.yaml; kubernetes/components/flux/sops; kubernetes/apps/vault; representative application secret resources.
- (decision) Persistent data is separated by storage intent: Longhorn is the default distributed block storage for application PVCs, while SMB-backed StorageClasses provide NAS/file storage for workloads that explicitly select them; local-path is a separate platform capability. A workload must declare the intended StorageClass rather than relying on an undocumented default when data placement matters. Evidence: kubernetes/apps/* PVCs, kubernetes/apps/kube-system/csi-driver-smb/ressources, kubernetes/apps/longhorn-system.
- (decision) External traffic follows the platform chain represented in manifests: MetalLB allocates LAN addresses, Traefik handles ingress routes, cert-manager issues certificates, and application resources select the traefik-ingresses class or Traefik CRDs. This prevents each workload from inventing a separate ingress and certificate path. Evidence: kubernetes/apps/network/metallb, kubernetes/apps/network/traefik, kubernetes/apps/cert-manager, representative workload ingress resources.
- (decision) Talos is the node operating system and talhelper is the configuration generator. talconfig.yaml and patches are the declarative node/cluster inputs; generated clusterconfig output is derived and ignored. Changes to Talos inputs require regeneration, validation, comparison with deployed machine configuration, and an explicit apply step. Evidence: talos/talconfig.yaml, talos/talenv.yaml, talos/patches, ansible/README.md, .gitignore.
- (version) The repository declares Talos v1.13.8 and Kubernetes v1.36.3 in talos/talconfig.yaml and talos/talenv.yaml. Kubernetes official release documentation shows the 1.36 minor line is maintained as of 2026-10-01; the repository version remains the source of truth for this cluster, not the latest upstream patch.
- (version) Flux is the selected GitOps controller and official Flux documentation confirms current Flux 2.9 GA and native support for Kubernetes resources, Kustomize, Helm, OCI and dependency management. The repository should document the installed Flux version from cluster state separately from the repository's architectural role.
- (assumption) README.md and the generated dependency graph reference cluster-meta and cluster-apps nodes, but matching paths are absent from the current kubernetes/apps tree. Treat these as stale/generated documentation or externally managed resources until cluster state or Git history confirms their ownership; do not present them as current repository paths without qualification.
- (question) The repository contains pg-dump, pg-dump-sync, pg-restore and Longhorn restore resources, but the authoritative recovery objectives, backup target, retention, restore validation cadence and acceptable downtime are not fully explicit in the manifests. Documentation must mark these operational guarantees as open until confirmed by the maintainer.
